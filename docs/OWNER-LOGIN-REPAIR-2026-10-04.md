# إصلاح دخول المالك — ٤ أكتوبر ٢٠٢٦

بدأ الفحص من `main` عند `22f5b87`، بحالة عمل نظيفة. نجح جلب GitHub وتبين أن النسخة المحلية مطابقة لـ`origin/main`. لم يُعد بناء المشروع من الصفر، ولم تُعدّل ملفات تصميمه أو بيانات العيادات الموجودة.

## ما ثبت أثناء الفحص

- احتوى `dist/owner.js` و`public/owner.js` نص `\n` حرفيًا خارج السلاسل في موضعين، مما تسبب في `SyntaxError` قبل تشغيل واجهة المالك.
- المعلومات السابقة عن الدالة لم تعد مطابقة للحالة: كانت `clinic-platform-admin` المنشورة بالإصدار 13 تدعم `list-owner-operations` ورسائلها العربية سليمة. لم يُعثر على نص علامات استفهام تالف في ملفات هذه النسخة.
- كان جدولا `owner_provision_operations` و`owner_deletion_receipts` غائبين بالفعل. أخفت الدالة ذلك باستجابة ناجحة وقوائم فارغة.
- فصلت نسخة GitHub التحقق الأولي من تحميل اللوحة جزئيًا، لكن طلبات العيادات والتعديل والتفعيل بقيت داخل `Promise.all` واحد؛ لم توفر كل الأقسام حالات فشل وإعادة محاولة مستقلة.
- كان الموقع المنشور بالإصدار 8 من مستودع Sites مستقل، بواجهة أقدم تختلف عن GitHub. ألغى مسار الدخول جلسته عند خطأ التحقق، وألغى النقل الجلسة عند 401 دون محاولة تجديدها. كانت أخطاء قوائم العيادات والتعديل تُلتقط داخل الأقسام؛ لذلك لا يصح نسبة كل HTTP 400 إلى إلغاء جلسة هذه النسخة.
- أثبتت السجلات استجابات 400 من نسخ سابقة من الدالة، لكنها لم تتضمن أجسام الطلبات. لم أستخدم كلمة مرور المالك الحقيقي؛ إعادة إنتاج الدخول وفشل الأقسام كانت باعتراض الطلبات في المتصفح، وليست تسجيل دخول حقيقيًا لذلك الحساب.
- استخدم إنشاء العيادة مسارًا قد يعيد تعيين كلمة مرور حساب سابق غير مرتبط. أُزيل هذا المسار لصالح إنشاء حساب جديد بسجل عملية قابل للمراجعة والتعويض.

## الإصلاح

أُصلحت صياغة السكربت، وفُصل تحميل العيادات والتعديل وتفعيل الأطباء والصيانة. تظهر رسالة عربية وزر إعادة محاولة داخل القسم المتعطل عند 400 أو500 أو انقطاع الشبكة. لا يظهر فشل تحميل العيادات كقائمة خالية أو إحصاءات صفرية. تبقى الجلسة عند الأعطال المؤقتة؛ يُرفض الوصول عند فشل الهوية أو صلاحية المالك الحقيقي. تشترك الطلبات في تجديد واحد، وتحاول إعادة الطلب مرة واحدة بعد 401. يمنع رقم جيل الجلسة ردود الطلبات المتأخرة من إعادة بيانات اللوحة بعد الخروج.

تميّز الدالة بين عدم السماح الحقيقي وفشل Auth أو قاعدة الصلاحيات المؤقت. أُضيفت رموز خطأ آمنة، منها `SESSION_INVALID` و`OWNER_FORBIDDEN` و`AUTH_UNAVAILABLE` و`OWNER_SCHEMA_NOT_READY`. لا تعيد الدالة رسائل SQL الخام أو مفاتيح أو كلمات مرور. الرسائل محفوظة بـUTF-8 وتُفحص قبل الرفع، وليس عبر استبدال علامات الاستفهام في الواجهة فقط.

تستخدم عملية الإنشاء `owner_prepare_tenant` ثم حساب Auth جديد ثم `owner_complete_tenant`. تعالج النتيجة الغامضة قبل التعويض، ولا تغيّر كلمات مرور الحسابات الموجودة. تبقى العيادة بانتظار التفعيل.

لم يُختبر حذف عيادة حقيقية أو تغيير كلمة مرور حساب حقيقي. اختبارات الحذف الموجودة نُفذت فقط في PostgreSQL والمتصفح المعزولين.

نجحت الصياغة لـ45 ملف JavaScript، وUTF-8 لـ19 ملف مصدر، وESLint دون تحذيرات، وTypeScript للواجهة، وDeno للدالة، وBuild للواجهة والموقع. فُصلت ملفات Deno عن `tsconfig` الخاص بالواجهة، وفُحصت ببيئتها الفعلية. أصلح الفحص أيضًا غياب قيد HTML لرابط العيادة بما يتوافق مع تحقق JavaScript وقاعدة البيانات.

## الحدود المتبقية

لم يُختبر دخول المالك الحقيقي أو إرسال رسالة SMTP أو فتح رابط الاستعادة من بريد حقيقي. اختبارات نجاح تسجيل الدخول والتجديد واستعادة كلمة المرور اعترضت شبكة Auth؛ فحوص PostgreSQL الحقيقية لا تثبت هذه المسارات الخارجية.

لا تزال `patient-booking` و`notification-dispatch` غير منشورتين، وجداول قدرات حجز الضيف وPush ومتطلبات كلمة مرور الطبيب غير موجودة في الإنتاج. نجاح محاكاة هذه الميزات لا يعني أنها تعمل في الموقع الحقيقي؛ لم تُنشر ضمن إصلاح المالك لتجنب توسيع تغييرات المخطط والواجهة الموجودة.

يبقى تاريخ المهاجرات القديمة مختلفًا بين المستودع والإنتاج. لا يمكن وصف المستودع بأنه نسخة مكتملة لإعادة إنشاء الإنتاج من الصفر. أظهر مستشار الأمان تنبيهات لدوال `SECURITY DEFINER` الموجودة وإيقاف حماية كلمات المرور المسربة؛ لا يثبت مجرد نجاح الاختبارات خلو المشروع من الأخطاء. الجداول الجديدة مقصودة بلا سياسات قراءة للمستخدمين، وممنوحة للخادم فقط. تفاصيل تنبيهات المستشار: https://supabase.com/docs/guides/database/database-linter و https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection.
